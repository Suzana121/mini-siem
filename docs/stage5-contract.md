## Shared interfaces
- Results directory `benchmarks/results/` holds JSON files written by tools; `benchmarks/RESULTS.md` is generated only by `python -m benchmarks.report` (bench stream). The report reads `engine.json`, `e2e.json` and, if present, `lab.json`, and renders missing files as "not run".
- `lab.json` schema (written by `lab/run_lab.py`, read by `benchmarks.report`):
  `{"generated_at": ISO8601, "commit": str, "scenarios": [{"name": str, "expected_rules": [str], "detected": bool, "missing_rules": [str], "unexpected_rules": [str], "time_to_detect_s": {rule_id: float} }]}`
- Log generator `benchmarks/gen_logs.py` exposes `generate(n_lines: int, seed: int = 1, attack_ratio: float = 0.02, start: datetime | None = None) -> tuple[list[str], list[GroundTruth]]` where `GroundTruth = {"rule_id": str, "source_ip": str, "line_index": int}`. Lines are valid BSD-syslog auth.log lines the existing parser (`app/parsers/auth_log.py`) understands, timestamps non-decreasing, attacks injected as bursts that satisfy the real rules in `rules/` (read them). Deterministic for a given seed.
- Existing API (see `app/main.py`): `POST /ingest` (Bearer API key, `{"source":"auth.log","lines":[...]}`, max 10,000 lines), `POST /auth/login` (cookie; non-GET needs header `X-Requested-With: mini-siem`), `GET /alerts?since=&q=&rule_id=&limit=`, `GET /stats/summary`, `GET /health`. `POST /api-keys {name}` (admin) returns the key once. Alert timestamps come from log event time.

## Lab stream requirements
Compose overlay `docker-compose.lab.yml` used as `docker compose -f docker-compose.yml -f docker-compose.lab.yml --profile lab up -d --build`:
- `victim`: debian-slim, openssh-server + rsyslog + sudo; accounts `deploy` (strong random password, set at build), `intern` (weak password present in a lab wordlist), root login over SSH enabled; hostname `victim01`; rsyslog writes `/var/log/auth.log` into named volume `lab-logs` (use ISO or BSD format, both are supported by the parser — verify against real output).
- `shipper`: built from the repo root image, runs `python -m scripts.ship_logs /lab-logs/auth.log --follow --url http://api:8000`, API key from env `SIEM_API_KEY`. `--follow` = poll-based tail starting at end or `--from-start`, handles truncation/rotation and partial last lines, batches up to 500 lines or 1s, retries with backoff on HTTP errors, never loses lines on retry.
- `lab-init` (one-shot, profile lab): uses `scripts/create_api_key.py` (admin login with `ADMIN_USERNAME`/`ADMIN_PASSWORD` against the API, creates a key named `lab-shipper`, writes it to a shared volume file) so the shipper can read it; document the flow in `lab/README.md`.
- `attacker`: hydra, nmap, openssh-client, netcat-openbsd, sshpass, python3; scenario scripts in `lab/scenarios/` and `lab/scenarios.yml` mapping scenario → script → expected rule ids. Networks: the lab services live on an `internal: true` network `lab-net`; only `api`, `shipper` and `lab-init` additionally join the default network so logs can be shipped. Attacker must have NO route to the internet or the host's other services; never target anything but `victim`.
- Scenarios and expected rules exactly as in the plan table (brute-force, spraying, brute-force-success, scanner, root-login, privesc, persistence, benign-noise). Each scenario script is idempotent/re-runnable (e.g. delete created accounts first) and prints its start marker; windows in rules are up to 10 minutes, so scenarios must trigger well within them.
- `lab/run_lab.py` (host-side runner, `--url`, `--admin-user/--admin-password` or `SIEM_API_KEY`-less login): runs each scenario with `docker compose exec attacker ...`, polls `GET /alerts?since=<scenario start>` every 1s up to a per-scenario timeout (default 90s) until all expected rules appear, computes time-to-detect = wall-clock from scenario start to first poll that sees the alert, collects unexpected rules from alerts since start, and writes `benchmarks/results/lab.json`; prints a table; exits non-zero if any expected rule is missing. Between scenarios use a different victim-side source or wait so dedup (DEDUP_WINDOW, default 15m) doesn't hide alerts: runner closes alerts of earlier scenarios via PATCH (analyst) or the lab sets `DEDUP_WINDOW=1s`—choose the simpler, document it.
- Unit tests (no Docker): tail/follow behavior, and runner scoring/timing logic with a fake alerts feed.
- Report mismatches between real sshd/sudo log text and the parser/rules to the coordinator (exact log lines + which rule failed) instead of editing `app/`.

## Bench stream requirements
- `benchmarks/gen_logs.py` as above; `benchmarks/machine.py` (CPU model, cores, RAM, OS, Python version, Docker settings if available, git commit) used by every tool's JSON header.
- `benchmarks/bench_engine.py`: offline, services not needed. Runs parse → enrich (use `samples/intel` plus a synthetic large feed of N CIDRs for the scaling test) → `DetectionEngine` → `score` → `MemoryAlertStore`, separately timed per stage, for 100k and 1M lines (CLI `--lines`, `--runs 3`, warm-up discarded, median reported), plus scaling over rules count (1, 6, 12, 48 duplicated rules) and intel feed size (10², 10⁴, 10⁶ entries). Report events/s, per-stage µs/event, peak RSS. Also checks detection correctness against `GroundTruth` (recall of injected attacks; extra alerts count). Output `benchmarks/results/engine.json`.
- `benchmarks/bench_e2e.py`: needs the compose stack up (`--url`, admin credentials or API key): (1) ingest throughput via `/ingest` by batch size (100, 1000, 10000) with several concurrent clients (httpx async), (2) detector drain rate: time until `GET /stats/summary`/event count reflects everything shipped (use `/events` or alert counts for completion), (3) ingest→alert latency p50/p95/p99 by injecting known attack bursts at a steady background rate and polling `/alerts` for each burst's rule/IP, (4) API read latency for `/alerts`, `/stats/summary`, `/stats/attack` with ≥ 10k stored alerts (generate via ingest). Output `benchmarks/results/e2e.json`. Must refuse to run against anything but localhost unless `--allow-remote`.
- `benchmarks/report.py` → `benchmarks/RESULTS.md` (machine info, commit, tables). Never hand-edit numbers.
- `python -m benchmarks.bench_engine --lines 20000 --runs 1` must run in well under a minute for tests; unit tests cover generator determinism, ground-truth validity (the engine detects each injected attack), report rendering with missing files. Add `benchmarks/README.md` (how to run, how to read the numbers, caveats). Do not run the e2e benchmark against the user's stack without it being up; if Docker isn't available just test the logic.
- Run `bench_engine` once at the end for real (1M lines may take minutes; use `--lines 200000 --runs 3` if 1M exceeds ~10 min) and leave `engine.json` for the coordinator.
